## 2. Decisions  (append; never reverse silently)

| Date | Decision | Why | Rejected alternatives |
|---|---|---|---|
| 2026-09-28 | Strict boundary isolation to `/root/ayu-back/mvp` | User directive: no access behind/outside mvp directory | Cross-directory linking or reference |
| 2026-09-28 | Service/Repository abstraction for all data access | Phase 0 & 1 requirement: API-ready architecture with seamless transition from browser mock to future backend | Hardcoded data in React components, direct mock imports in UI |
| 2026-09-28 | Separate Role Permissions from Access Scope | CTMS domain requirement: a role's permissions (e.g. View Patients) must be decoupled from data scope (e.g. Assigned Site vs Assigned Participants) | Flat global permissions |
| 2026-09-28 | Browser-only synthetic data execution | Security & compliance: no clinical data leaks, zero external telemetry or cloud dependencies | External mock APIs, unvetted third-party services |
| 2026-09-29 | Vite 6 + React 19 + TypeScript + Tailwind 3.4 | Standard client-side SPA architecture, fast HMR, reliable verification ladder, native ES modules | SSR frameworks with server requirements |
| 2026-09-29 | Dedicated Participant Detail Route (`/pi/patients/:participantId`) | Direct deep linking and clear breadcrumb navigation fitting existing routing architecture | In-page modal or nested tabs |
| 2026-09-29 | Deterministic Reference Date Provider (`getReferenceDate()`) | CTMS operations reproducibility: enables stable calculation of visit windows and operational statuses (DUE, OVERDUE, MISSED) across automated tests and browser UI | Dynamic unmocked `new Date()` |
| 2026-09-29 | Protocol Target Offset vs Allowable Window Separation | Clinical trial accuracy: a visit has a target date (e.g. Day 28) and an allowable compliance window ($\pm3\text{d}$); status transitions to OVERDUE or MISSED after window closure | Treating target date as hard cutoff without window |
| 2026-09-29 | Decoupling Severity, Seriousness, and Causality | ICH-GCP E2A / E6 clinical regulatory compliance: Severity describes symptom intensity (Mild/Moderate/Severe), Seriousness is a defined regulatory outcome (Death/Hospitalization/Disability/Life-threatening/Medically Important), and Causality is a medical assessment (Unlikely/Possible/Probable/Definite). Severe $\ne$ Serious. | Conflating severity with seriousness, auto-deriving seriousness from severity |
| 2026-09-29 | Non-Diagnostic Human-in-the-Loop Causality Assessment | Medical ethics & regulatory law: CTMS prototype must not perform automated clinical diagnosis; Causality assessment remains an investigator-entered and PI-signed medical determination. | Automated AI diagnosis or algorithmic causality scoring |
| 2026-09-29 | Protocol Deviation Scoping (`PARTICIPANT` vs `SITE` vs `STUDY`) | Clinical trial protocol deviations occur at subject level (e.g. out-of-window visit, missed test), site level (e.g. temperature excursion in drug storage, missing calibrated equipment), or study level (e.g. delayed ethics amendment submission). `participantId` is strictly optional and only populated when `scope === 'PARTICIPANT'`. | Forcing a dummy participant ID onto site-level deviations, restricting deviations to participants only |
| 2026-09-29 | Decoupling Deviation Classification from Safety Severity | ICH-GCP E6 (R2) compliance: Deviation classification (`MINOR`, `MAJOR`, `CRITICAL`) measures protocol / GCP non-compliance and impact on trial integrity or subject safety, while AE Severity (`MILD`, `MODERATE`, `SEVERE`) measures clinical symptom intensity. Protocol deviations must never be styled or categorized as Adverse Events. | Sharing severity types between safety and compliance, conflating protocol deviations with adverse events |
| 2026-09-29 | CAPA Status Independence from Deviation Lifecycle | CAPA (Corrective and Preventive Action) represents an operational mitigation workflow (`NOT_REQUIRED`, `PENDING`, `IN_PROGRESS`, `COMPLETED`, `OVERDUE`) that runs alongside or triggers lifecycle progression (`REPORTED`, `UNDER_REVIEW`, `ACTION_REQUIRED`, `CAPA_IN_PROGRESS`, `RESOLVED`, `CLOSED`). Resolving CAPA moves lifecycle towards resolution while preserving CAPA historical record. | Conflating CAPA status with deviation status into a single field |
